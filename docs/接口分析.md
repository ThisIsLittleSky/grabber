# 选课系统接口分析

这是正方教务系统（ZFSoft）的选课模块接口，`60.8.3.210:8090` 是 nginx 反代，`backendIP: 127.0.0.1:8080` 暴露了后端。这套接口在设计上就是冲着防自动化去的。

## 1. 最核心的"狡猾"：双重教学班 ID

每个教学班有两个 ID，这是整个设计的关键：

```
jxb_id      = 5706B5A0B5F80E52E0630B02FD0A792D   ← 32位，可读的UUID
do_jxb_id   = 0b0771813105bb91168840266facf99a... ← 256位十六进制(128字节)，加密串
```

- **列表接口**（请求15 PartDisplay）只给 `jxb_id`，**不给** `do_jxb_id`
- 必须再点一次展开详情（请求16 `cxJxbWithKchZzxkYzb`）才能拿到 `do_jxb_id`
- **真正提交选课**（请求17 `xkBcZyZzxkYzb`）用的 `jxb_ids=` 参数，就是这个 256 位的加密串

也就是说：**你无法凭空构造选课凭证**，必须先实时抓列表 → 展开详情 → 把那个加密串原样回传。128 字节的加密串（AES 一类的对称加密，大概率含 `jxb_id + 时间戳 + 随机IV + 规则`），服务器解密校验。随机 IV 意味着**每次请求返回的 `do_jxb_id` 都可能不一样**，没法缓存复用，必须当场取。

## 2. 选课是多阶段的流水线，不是一次 POST

真正的选课链路：

```
① cxZzxkYzbPartDisplay      列表查询  → tmpList
② cxJxbWithKchZzxkYzb      展开详情  → 拿到 do_jxb_id / xkkz_id
③ zzxkyzb_cxXkTitleMsg     前置探针  → {"flag":"1"} 才放行   ← 假动作
④ zzxkyzbjk_xkBcZyZzxkYzb  真正提交  → {"flag":"1"} 或冲突报错
```

- ③这个"title msg"接口是典型的**廉价探针**：先花一次请求探测你这会儿能不能选、有没有超时、参数对不对，不对就提前挡掉，真正的提交接口就少被打。
- ④返回 `flag:0` + 具体错误（比如"上课时间与其他教学班有冲突"），**冲突检测在服务端做**，不是你本地能算出来的。

## 3. 退选/改选也是多步

```
check是否在选课时间 → tuikBcZzxkYzb(退) → xkBcZypx(批次刷新) → 重新走③④
```

退选（`tuikBcZzxkYzb`）要带 `kch_id + jxb_ids(加密) + xkxnm + xkxqm + txbsfrl`，每一步都校验。

## 4. 全上下文校验——防伪造、防换号

提交选课时要拼上一大串学生维度参数：

```
jg_id(学院) zyh_id(专业) zyfx_id(专业方向) bh_id(班级) njdm_id(年级)
xz(学制) ccdm(层次) xbm(性别) mzm(民族) xslbdm(学生类别) xsbj(学生标志)
bklx_id(本科类型) sfkkjyxdxnxq xqh_id(校区) ...
```

这些会跟 JSESSIONID 绑定的真实学生档案做比对，**任何一项跟 session 对不上就拒**。所以想"换一个学号选课"或者拼漏参数都不行。

## 5. 会话与防缓存

- `JSESSIONID` + `route` 两个 cookie：`route=5958c386...` 是负载均衡的 **sticky session**，保证请求都打回同一台后端。
- 所有请求统一带 `gnmkdm=N253512`（功能模块号），服务端按它做权限白名单。
- 通用查询带了 `nd=1787319369481&time=0`（时间戳+固定值）破缓存。
- 请求头强制带 `referer` 指向选课页 + `origin`，`x-requested-with: XMLHttpRequest`，跨域策略 `strict-origin-when-cross-origin`。

## 6. 选课规则串 `xkgz`

列表里每条课带一个规则串，比如：

```
xkgz = 1~0~0~1~5960666114DB1C17E0630B02FD0A8BCE~0~0
       ↑  ↑ ↑ ↑ ↑───────────────┬──────────────↑
       参数  ...    xkkz_id(选课控制ID)   ...
```

中间的 `xkkz_id` 把每个选课实例**绑到具体的选课轮次**。提交和退选都要带它，服务器据此判断你这笔操作是不是在当前开放的轮次里——**过了选课时间窗口，光靠接口直接打也是拒的**。

## 结论：想自动化，最难啃的几块

1. **每轮都要实时抓加密的 `do_jxb_id`**，不能缓存、不能伪造——这是最大的门槛。
2. 必须**完整复刻选课流水线**（列表→详情→探针→提交），少一步都不行。
3. **JSESSIONID 时效**：会话过期就要重登，无法跨会话保持。
4. 服务端**全上下文 + 轮次 + 冲突三重校验**，参数拼不全就白打。

一句话总结：它把所有"可预测"的东西（教学班ID、选课规则、提交参数）要么加密、要么拆成多步、要么绑死会话，目的就是让"抓包直连"的脚本没法用写死的参数跑起来。如果想做选课辅助，核心思路应该是**在浏览器里做 DOM 级自动化**（复用页面已有的 session 和加密逻辑），而不是绕开它。
